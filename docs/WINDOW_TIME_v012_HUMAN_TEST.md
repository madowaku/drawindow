# 窓辺の時間：本人試遊と２人以上のパイロット

## 順序

最初に開発者本人がA/B/Cを試す。自動操作は本人試遊として数えない。その後、本人以外の少なくとも２人で探索的に比較する。まだ本人の評点・パイロット回答は入力されていない。v0.11の「違いがわからない」「動きを戻すと忙しい」という利用者報告は設計の起点であり、v0.12の採用判定には流用しない。

## 本人の試遊

1. `/?window-time` を開き、OS状態の表示を確認する。Windowsの「アニメーション効果OFF」は動き軽減として尊重される。テンポを変えても解除されない。動きを試すかどうかは本人がOS側で選ぶ。
2. まず同じ絵・同じDAYでA/B/Cを並べる。「再生する」で窓へ移る。1.2秒前後で終わるAと、筆数に応じて長くなるB/Cを観察する。再生/停止/シークで、線の途中と指先が一致しているか見る。
3. 一本線の絵と、筆数の多い絵を選ぶ。最後の線、ペンを離す瞬間、次の線への間が自然かを見る。速度/ためらいを変えた場合は、初期設定の比較と別の条件として記録する。
4. NIGHTでも繰り返す。夜は速い昼のコピーではなく、息・間・身体の小ささが違う。表情を増やして意味を説明していないか、描く相手の存在感が薄れていないかを見る。
5. 「５往復を試す」でA/B/Cを各１回、始まりから「またね」まで遊ぶ。操作を遅くしないこと、完成後は自分のタイミングで次へ進めることを確認する。研究条件はSTART時に固定される。次の条件は結果から最初へ戻って選ぶ。
6. BGMも本人がONにして確認する。音楽の速度は変わらない。息やturnの効果音が急かさないか、夜の静かな線に合っているかを聞く。ブラウザーによる音源デコード成功は聴感評価の代わりではない。
7. フォームは1=全くそう思わない、5=とてもそう思う。「急かされる」「長すぎる」は高いほど懸念。単純合計しない。未試遊の条件、単体絵しか見ていない「またねまで」は空欄にする。
8. 本人の操作で評価JSONを保存する。単体比較と５往復の感想は別のファイルにする。終了後の記録再生は同じ認識結果を使うが、実際に相手と過ごした時間の代用にはしない。

## ２人以上のパイロット

事前に「Bが改良版」「夜のほうが良い」などと説明しない。「３つの時間の過ごし方を比べます。好きなものがなくても構いません」と伝える。条件名は速度の説明であり優劣ではない。

参加者１はA→B→C、参加者２はC→B→Aなど提示順を反転する。DAY/NIGHTも同じ人が両方見るか、順序と合わせて記録する。まず同じ絵/同じ記録を比較し、次に実際の５往復を遊ぶ。自由プレイの絵・認識結果・描き直しが異なることを演出の効果と混ぜない。可能なら初回は全て初期値、二度目だけ本人が調整する。

確認項目はフォームの８項目。最後に「もう少し一緒にいたいと思ったか」「どの場面でそう感じたか」「どこで退屈/急ぎを感じたか」を本人の言葉で聞く。意味を教えたり、期待した反応へ誘導したりしない。少人数の印象を統計的な優位と呼ばない。

## 記録と限界

- 感想と表示/操作/visibility/endingのログは本人が保存するときだけローカル出力。自動送信なし。評価JSONに絵・意図名・認識語は入れない。描画入り再生JSONは別チェックと保存操作でのみ出力する。
- 自動記録の表示機会は、注視・気づき・楽しさの証明ではない。フォームに答えただけで本人が全条件を試したとは仮定しない。
- 途中保存にはゲームと研究条件を保持する。復元した試行はpartialで、以前の演出ログ/感想を補完しない。中断した試行を連続５往復のテンポ評価へ混ぜない。
- 動き軽減中は完成絵表示になる。その試行はアクセシビリティ/操作評価として残し、指先の自然さの比較から分ける。
- Android実機の指/ペン、背景復帰、出音、機内モードは別途受入。360pxのChromiumは実機ではない。

## 採否

現時点の標準候補はB。ただし技術的に線を追える時間を確保しつつCほど長くないという仮説であり、人間の好みの根拠ではない。本編はAを維持し、Dも保留する。Bでしずくの存在感が薄れたり、待つほうがつらくなったりしたらAを維持する。別々に良い部分があった場合も、同時に全パラメータを変えず、次の比較は一つの要素に絞る。
